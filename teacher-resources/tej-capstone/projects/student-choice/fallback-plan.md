# Student-Designed Project — Fallback Plan

Choose the fallback during proposal approval, not after the deadline.

## Fallback A: substitute the input

Replace an unavailable sensor with a pushbutton, switch, or teacher-approved potentiometer. Preserve the same state machine and output behaviour. Recalculate the interface and label the substitution.

## Fallback B: simulate the input

Run the state machine from keyboard, command-line, or synthetic data. Complete unit/state tests and document the intended hardware adapter. Add one safe physical LED output if possible.

## Fallback C: adopt a class-stock pathway

Move to the minimum automatic night light, Linux alarm, or traffic-light pathway. Reuse completed proposal, interface, and test-plan work where it remains relevant.

## Fallback D: measured subsystem plus simulated integration

Complete one physical input or output subsystem with voltage evidence. Simulate the unavailable remainder and clearly distinguish physical, simulated, and predicted evidence.

## Evidence equivalence

Every fallback still requires:

- one approved low-voltage circuit;
- Linux/Python behaviour;
- schematic and interface table;
- calculations and measurements;
- staged test plan;
- fault diagnosis and revision;
- portfolio conclusion against revised criteria.

Changing to a fallback is a documented design decision, not a penalty. Invented measurements or an unsafe rushed substitution are not acceptable alternatives.
