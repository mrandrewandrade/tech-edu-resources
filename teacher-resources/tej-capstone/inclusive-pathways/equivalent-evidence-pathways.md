# Inclusive and Equivalent Capstone Pathways

## Principle

Change access, representation, pacing, or response format while preserving the intended learning. Students do not all need to perform identical physical actions, use a horn, publish publicly, or work under the same sensory and motor conditions.

Every pathway should still produce evidence of:

- design and schematic/system reasoning;
- safe practice and component/interface boundaries;
- Linux/Python input-decision-output behaviour;
- voltage/circuit measurements or valid interpretation of supplied measurements;
- KVL/KCL or other suitable circuit reasoning;
- testing/troubleshooting;
- revision;
- technical communication and individual explanation.

## Five equivalent pathways

| Pathway | Student experience | Suitable evidence | Boundary |
|---|---|---|---|
| **Physical build** | Constructs and tests the approved low-voltage circuit | Power-off inspection, measurements, code tests, fault/correction, demonstration | Do not make dexterity/speed the hidden criterion |
| **Simulation plus analysis** | Builds/tests a faithful simulator circuit and analyzes provided/observed behaviour | Schematic, predicted/simulated values, KVL/KCL, inserted fault, revision | Simulation is identified as a model, not claimed as physical measurement |
| **Keyboard-driven software simulator** | Runs the same state-machine logic using keyboard/file inputs and terminal outputs | Python tests, states/events, logs, boundary cases, hardware interface plan | Must still explain the real electrical boundary and proposed tests |
| **Diagnostic/reference circuit** | Investigates an existing safe circuit rather than assembling every connection | Predictions, named test points, measurements, fault tree, correction recommendation | Student must not receive the diagnosis in advance |
| **Documentation/system integration** | Coordinates schematic, BOM, tests, data, code explanation, and portfolio while a partner performs some physical manipulation | Individual explanation, calculation, analysis, code/test ownership, evidence integration | Cannot become decorative work detached from technical understanding |

Pathways can be combined. For example, a student can write and test the Python state machine, interpret a partner’s approved voltage measurements, and personally diagnose an inserted fault on a reference trainer.

## Evidence equivalence by criterion

| Criterion | Physical evidence | Equivalent non-identical evidence |
|---|---|---|
| Design/schematic | Builds from own approved diagram | Annotates/corrects a diagram and justifies ratings/interfaces |
| Safe construction | Performs staged inspection and energizing | Leads a power-up review, identifies hazards, and authorizes/withholds power using evidence |
| Linux/Python | Controls physical input/output | Uses hardware-independent adapters with the same state logic and tests |
| Measurements | Connects meter to named test points | Interprets teacher/partner measurements, predicts missing values, identifies invalid measurement setup |
| KVL/KCL/reasoning | Verifies own circuit | Analyzes equivalent topology or supplied data with named loops/nodes |
| Troubleshooting | Diagnoses own build | Diagnoses an inserted reference/simulator fault without prior answer |
| Revision | Changes physical/code design | Revises schematic, code, test plan, accessibility, or component choice based on evidence |
| Communication | Demonstrates and presents | Uses recorded demo, live diagnostic walkthrough, accessible portfolio, or individual conference |

## Fine-motor access

Possible supports:

- larger breadboards/components, pre-stripped jumpers, lead-forming tools, labelled relay sockets;
- partner places parts while student directs topology, verifies nodes, controls test plan, and explains evidence;
- simulation/diagnostic pathway for dense headers or fragile jumper work;
- extra setup time without reducing conceptual expectations;
- photographs/diagrams enlarged before physical placement;
- alternatives to soldering when soldering is not the assessed expectation.

Do not grade steadiness, speed, or neatness unless a documented course expectation and appropriate access support make it relevant.

## Vision and colour access

- Use large-print schematics, high contrast, thick conductors, and readable reference designators.
- Do not use wire colour as the only identifier; add labels and test-point names.
- Provide tactile/physical orientation descriptions where appropriate.
- Read meter values aloud or use an accessible display while preserving student interpretation.
- Provide digital source diagrams that can zoom without losing quality.
- Describe LED states with labels/log output, not colour alone.

## Hearing and sound sensitivity

- Replace the horn with a lamp, quiet buzzer, vibration, terminal output, or logged alarm event.
- Announce any horn demonstration and permit distance/exit/hearing protection consistent with school practice.
- Never require a student to tolerate the horn to demonstrate equivalent learning.
- Caption videos and provide written demonstration sequences.
- Use visible turn-taking and written station instructions in a noisy lab.

## Attention and executive-function support

- Give one-page staged checklists and mark the current gate.
- Use visible timers with warning before transitions.
- Keep component bins small and labelled.
- Freeze optional features once minimum evidence is at risk.
- Require one test and one recorded conclusion before changing another variable.
- Use short teacher check-ins tied to the design log.
- Provide a defined restart point after interruption.

## Reading and language support

- Pair concise instructions with diagrams and teacher modelling.
- Define relay, GPIO, reference/ground, node, loop, state, input, output, and driver in the project context.
- Provide sentence frames for evidence: “I expected ___ because ___. I measured/observed ___. This rules out ___, so the next test is ___.”
- Permit oral explanation/conference with teacher notes or recording where approved.
- Keep performance language separate from dense technical source documentation.
- Teach how to locate part number, pinout, absolute maximum, recommended condition, and typical application in a datasheet.

## Anxiety and presentation access

- Publish demonstration criteria and questions in advance.
- Allow a teacher-only or small-group demonstration.
- Permit recorded operation followed by a live individual explanation.
- Use a diagnostic walkthrough when repeated public operation would risk the hardware.
- Separate sound/noise exposure from technical assessment.
- Permit notes, schematic, code, and design log during explanation.

## Attendance and interrupted access

- Use the daily design log to preserve continuity.
- Store approved shared evidence where absent students can access it without private information.
- Let returning students complete individual code tests, schematic tracing, measurement interpretation, or diagnostics.
- Distinguish team observations from the student’s own observations.
- Use January 25–26 for missed conferences/demonstrations.
- Reduce optional features before extending work into assessment days.

## Quiet alternative to the horn

The quiet pathway uses the same control logic and circuit reasoning with:

- a 12 V indicator lamp at the relay contacts;
- a low-current active buzzer through an approved driver;
- an LED plus terminal/log message; or
- a simulator output showing relay state and expected load current.

Students still identify coil versus contact circuits, fuse/protection, driver, flyback path, source/load current, relay state, KVL loops, and KCL nodes. The acoustic output is not the learning expectation.

## Avoid these false equivalents

- Colouring a worksheet instead of analyzing a circuit.
- Copying a teammate’s code without explaining or testing it.
- Watching a demonstration without making predictions or interpreting evidence.
- Writing a general research report instead of designing/testing/troubleshooting.
- Giving full marks for documentation when required technical understanding is absent.
- Requiring public disclosure as evidence of communication.

## Teacher documentation

Record:

- intended learning held constant;
- access barrier or equipment limitation;
- pathway/format selected;
- evidence the student will produce;
- individual accountability method;
- review date and whether the pathway remains effective.

Follow current student plans, school/board processes, and professional judgement. This guide supports planning; it does not replace individual accommodations or specialized advice.
